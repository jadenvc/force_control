# Floating-gripper FlipUp: compliance, force sensing, impedance, and teleoperation

Last updated: 2026-08-17

This note documents the current Force Dimension → floating WSG50 FlipUp stack,
what each stiffness/compliance parameter means, what is actually recorded, and
the engineering interventions used to make force-aware demonstrations stable and
reasonably realistic.

The most important distinction is that the stack contains **four different
notions of stiffness**:

| Layer | Current control/field | Meaning |
| --- | --- | --- |
| MuJoCo contact | `solref`, `solimp`, `--tip-softness` | Numerical/physical compliance of the fingertip contact constraint |
| Simulated gripper | `--tool-kp` | Cartesian impedance stiffness driving the floating gripper toward the operator's pose |
| Haptic handle | `--stiffness`, `--force-gain` | How stiff contact feels at the Force Dimension handle |
| Training label | `stiffness_0` | Post-processed adaptive-compliance label inferred heuristically from force; not a measured or commanded stiffness |

Changing one does not generally have the same effect as changing another.

## 1. Current recommended command

The most recently tested collection configuration was:

```bash
python teleop/teleop_floating_flipup.py \
  --collect-dataset ~/data/flipup_floating_1khz_try.zarr \
  --auto-finish \
  --render-quality fast \
  --view-fps 30 \
  --scale 3 3 3 \
  --force-rate 60 \
  --tool-kp 4000 \
  --tip-softness 1.0 \
  --force-sensor-cutoff 30
```

With `--tool-kp 4000`, scale 3, and default handle stiffness 1800 N/m,
the automatically derived haptic gain is:

```text
force_gain = 1800 / (4000 × 3) = 0.15 handle N / sim N
```

Passing the same option more than once is legal argparse behavior: the last
value wins. For example, `--tip-softness 0.5 --tip-softness 1.0` resolves to
`1.0`.

## 2. What the floating-gripper controller models

The floating version removes the UR5e and models the WSG50 assembly as a free
rigid-body system. It retains:

- the WSG50 collision and visual geometry;
- approximately 1.89 kg of physical moving mass and its rotational inertia;
- the camera, book, table, and bookend;
- gravity on the book and all contact dynamics;
- six-degree-of-freedom gripper motion and optional wrist orientation input.

It removes:

- arm joints and joint torque limits;
- manipulator Jacobians and singularities;
- arm joint damping and arm tracking artifacts;
- the unrealistically large forces caused by a stiff arm lagging several
  millimeters behind its task-space target.

Gravity is cancelled body-by-body for the floating gripper only. The book still
has gravity. Cancelling each gripper body's weight also cancels the corresponding
gravity moments without requiring an arm inverse-dynamics model.

For FlipUp, both WSG50 finger sliders are projected to the closed state after
every physics step. This prevents contact from back-driving the fingers and
causing the earlier constant opening/closing chatter. The gripper is therefore
nonprehensile and rigidly closed for this task.

## 3. `tool_kp`: simulated Cartesian impedance

The floating gripper uses direct Cartesian PD/impedance control. Translation is:

```text
F_controller = tool_kp × (x_target - x_tool) - tool_kd × v_tool
```

Rotation is analogous:

```text
τ_controller = tool_rot_kp × rotation_error - tool_rot_kd × ω_tool
```

The wrench is applied directly to the floating gripper base. Contact forces are
still generated by MuJoCo at the actual fingertip contact locations.

`--tool-kp` is therefore the proportional stiffness of the **simulated robot
controller**, in N/m. At 4000 N/m:

- 1 mm of positional error corresponds to 4 N of spring force;
- 5 mm corresponds to 20 N before damping and rigid-body dynamics;
- 8 mm corresponds to 32 N.

Translational damping is derived automatically from gripper mass:

```text
tool_kd = 2 × damping_ratio × sqrt(tool_kp × gripper_mass)
```

With damping ratio 1.05 and gripper mass about 1.89 kg:

- `tool_kp=5000` gives about 204 N·s/m;
- `tool_kp=4000` gives about 183 N·s/m;
- lowering `tool_kp` also lowers the automatically derived damping.

Lower `tool_kp` makes the simulated gripper more compliant and normally reduces
contact force for the same operator target penetration. It also increases
tracking error and can make the tool lose the book edge. It changes the task
dynamics and the recorded forces; it is not merely a feel adjustment.

## 4. How `tool_kp` differs from “teleop kp”

There is no CLI option literally named `teleop-kp`. In this stack, “teleop kp”
usually means `--stiffness`: the desired translational stiffness rendered at the
physical haptic handle.

The upper-bound relationship is:

```text
k_handle = tool_kp × position_scale × force_gain
```

If `--force-gain` is omitted, the program derives it as:

```text
force_gain = requested_handle_stiffness / (tool_kp × position_scale)
```

Consequences:

- `--tool-kp` changes simulated motion, simulated force, and contact behavior.
- `--stiffness` changes how strongly the operator feels a given displacement.
- `--force-gain` changes handle newtons per simulated newton directly.
- Lowering `tool-kp` while leaving `--stiffness 1800` causes `force-gain` to
  increase, so simulated forces can decrease while the handle still feels solid.

For the current settings:

```text
tool_kp = 4000 N/m
scale = 3
force_gain = 0.15 N/N
k_handle = 4000 × 3 × 0.15 = 1800 N/m
```

Two other springs should not be confused with either controller:

- `--collection-recenter-stiffness` is an idle-only spring that pulls the
  physical handle to dataset home. It is disabled during demonstrations.
- `stiffness_0` is a generated learning label described below; it does not drive
  the simulation or haptic device.

## 5. Fingertip softness

`--tip-softness` is a normalized convenience knob in `[0, 1]`. It changes only
the two fingertip-pad collision geoms. It does not change the book, table,
bookend, gripper controller, force sensor, or haptic gain.

The knob linearly interpolates these resolved parameters:

| `--tip-softness` | `solref` time constant | `solref` damping ratio | `solimp` width |
| ---: | ---: | ---: | ---: |
| 0.0 | 10 ms | 1.0 | 3 mm |
| 0.5 | 15 ms | 1.5 | 4 mm |
| 1.0 | 20 ms | 2.0 | 5 mm |

This is not a direct Young's modulus or calibrated silicone material model. It
is a controlled way to make the MuJoCo contact constraint respond more like a
compliant fingertip.

### 5.1 `solref`

With positive MuJoCo `solref`, the two values are approximately:

```text
solref = [time_constant, damping_ratio]
```

- A larger time constant makes the constraint correct penetration more slowly
  and therefore makes contact softer.
- The damping ratio controls transient damping around that constraint response.
  A value near 1 is critically damped in the reference model; values above 1 are
  more heavily damped.

`solref` controls the dynamics of constraint correction. It is not the same as
the Cartesian `tool_kp` spring.

### 5.2 `solimp`

MuJoCo `solimp` shapes constraint impedance as a function of constraint
violation/penetration. Its five conceptual entries are:

```text
solimp = [d0, d_width, width, midpoint, power]
```

The current softness knob changes only `width`; the other entries retain the
compiled fingertip values. Increasing width spreads the impedance transition
over more penetration, producing a more gradual, pad-like contact onset.

In plain language:

- `solref` controls how quickly and how dampedly the solver tries to remove
  penetration;
- `solimp` controls how the constraint becomes stiff across the penetration
  region;
- `tool_kp` controls how hard the robot continues driving into that contact.

Making contact softer can reduce impact and force chatter, but it can also allow
more geometric penetration. The position controller may then push farther until
its commanded force again balances the object/contact load. Therefore softer
`solref`/`solimp` does not guarantee an equal reduction in sustained force.

## 6. The force sensor model

The floating gripper does not have a physical wrist cut, so the base signal is
the exact MuJoCo contact wrench summed over all robot contacts and transported
to the tool origin:

```text
[Fx, Fy, Fz, Tx, Ty, Tz]
```

That raw wrench contains millisecond-scale changes from contact activation,
friction-state changes, and solver constraint impulses. A real F/T sensor has
finite mechanical/electrical bandwidth, so the optional sensor model applies
two cascaded first-order low-pass poles in the tool frame.

For each pole:

```text
tau = 1 / (2π × cutoff)
alpha = 1 - exp(-dt / tau)
stage1 += alpha × (raw - stage1)
stage2 += alpha × (stage1 - stage2)
sensor = stage2
```

At `--force-sensor-cutoff 30` and `dt=1 ms`:

- each pole has a 30 Hz cutoff;
- `alpha ≈ 0.1718`;
- the cascade is -6 dB at 30 Hz;
- the cascade's overall -3 dB point is about 19.3 Hz;
- 50% step response is about 8.9 ms;
- low-frequency group delay is about 10.6 ms.

### 6.1 Does 30 Hz mean forces are recorded at 30 Hz?

**No.** It means the sensor has approximately 30 Hz per-pole bandwidth. The
sensor state is updated every 1 ms and its output is recorded every 1 ms.

With the default collection settings:

| Signal | Sample/storage rate | Bandwidth/processing |
| --- | ---: | --- |
| Raw MuJoCo wrench | 1000 Hz | Solver-exact, no sensor filtering |
| Modeled sensor wrench | 1000 Hz | Two-pole low-pass, normally 30 Hz per pole |
| Robot state and commands | 1000 Hz | One sample per simulation tick |
| Haptic servo | Approximately 1000 Hz | Independent Force Dimension thread |
| RGB | Approximately 28–30 Hz | Asynchronous; stored only for genuinely new frames |

A 30 Hz signal sampled at 1000 Hz has many samples across each resolvable force
variation. This is desirable: it preserves causal timing and lets training code
subsample later without rerunning the simulator.

### 6.2 Recorded wrench channels

The important dataset channels are:

| Array | Rate | Meaning |
| --- | ---: | --- |
| `wrench_0` | 1000 Hz | BC-facing modeled sensor wrench in the tool frame |
| `wrench_sensor_model_0` | 1000 Hz | Explicit copy of modeled tool-frame sensor wrench |
| `wrench_sensor_model_world_0` | 1000 Hz | Modeled sensor wrench in world axes |
| `wrench_ground_truth_0` | 1000 Hz | Raw solver contact wrench in the tool frame |
| `wrench_ground_truth_world_0` | 1000 Hz | Raw solver contact wrench in world axes |
| `device_force_cmd` / `haptic_force_sent` | 1000 Hz numeric log | Force commanded to the handle |
| `wrench_filtered_0` | 1000 Hz | Additional slow causal moving average used for adaptive labels |

`--force-sensor-cutoff 0` makes the modeled sensor an identity path, so
`wrench_0` follows raw contact.

The separate default `--dataset-wrench-filter 0.25` applies a 250 ms causal
moving average to `wrench_0` when the episode is committed. It does not reduce
the array's 1000 Hz sample rate. It creates `wrench_filtered_0` and is used only
to generate the compatibility adaptive-compliance labels. It is much slower
than the 30 Hz sensor model and should not be mistaken for the live sensor.

## 7. What force the operator feels

The default haptic force source is `contact`, which uses raw solver contact
force rather than the delayed sensor model. The pipeline is conceptually:

```text
raw sim contact force
  → sim-force clip
  → world/device axis transpose
  → force gain
  → short haptic low-pass (`--force-tau`)
  → force slew limit (`--force-rate`)
  → handle magnitude clamp (`--max-force`)
  → Force Dimension 1 kHz servo
```

The default raw haptic path is deliberate: putting sensor delay inside a stiff
bilateral feedback loop reduces passivity margin. `--force-source wrist` makes
the floating controller reflect the modeled sensor instead, but this is an
explicit experiment and should use lower handle stiffness plus `--diagnose`.

Important haptic-only knobs:

- `--stiffness`: requested handle stiffness, currently 1800 N/m for floating.
- `--force-gain`: handle N per simulated N; normally derived automatically.
- `--force-tau`: live handle-force smoothing, default 2 ms. More lag can reduce
  visible ripple but reduce passivity.
- `--force-rate`: maximum change of handle force in N/s. It softens contact onset
  without changing the steady simulated force. The recent runs used 60 N/s.
- `--max-force`: physical handle-force magnitude cap, default 10 N.
- `--damping`: contact-dependent haptic velocity damping, default 30 N·s/m.
- `--force-clip`: simulated-force ceiling used only by reflection, not a physical
  limit on MuJoCo contact.

The conservative sampled-data passivity check is:

```text
k_handle < 2 × handle_damping / (1/control_rate + 2 × force_tau)
```

At 1000 Hz, 2 ms force filtering, and damping 30, the printed limit is about
12000 N/m. A handle stiffness of 1800 N/m has about a 6.7× margin.

## 8. Current force results

### 8.1 Before the latest reduction

Recent episodes with:

```text
tool_kp=5000, tip_softness=0.5, sensor=30 Hz
```

had approximately:

- pivot sensor median: 18.8 N;
- p95: 35.4 N;
- maximum: 42.1 N.

### 8.2 Current configuration

Four successful episodes with:

```text
tool_kp=4000, tip_softness=1.0, sensor=30 Hz
```

had:

- pivot sensor median: 15.6 N;
- p75: 22.0 N;
- p95: 27.0 N;
- maximum: 31.4 N;
- handle median/p95: about 3.0/4.6 N.

Force remained angle-dependent:

| Book angle interval | Sensor-force median |
| --- | ---: |
| 85° → 70° | 24.5 N |
| 70° → 50° | 17.4 N |
| 50° → 30° | 9.2 N |
| 30° → 15° | 6.3 N |

The largest remaining load is initial geometric wedging, not the final lift.

Contact-state reconstruction at the early pivot peak found:

- 22–31 N projected along the fingertip/book contact normal;
- 9–11 N tangential component;
- approximately 2.2–2.4 mm of solver contact penetration.

Lowering friction is therefore unlikely to solve the main load and could make
the finger slip. Reducing normal target penetration is the more direct fix.

The true first 100 ms after touch was usually already modest: raw peaks were
8.1, 9.6, 33.2, and 14.6 N across the four episodes. The 30 Hz sensor reported
7.0, 8.7, 17.9, and 12.9 N. In three episodes the force exceeded 20 N only after
190–235 ms of continued pushing. This separates one true impact from the more
common sustained-wedging problem.

## 9. Adaptive compliance and `stiffness_0`

The current demonstrations do **not** contain a stiffness selected or directly
measured from the human. `tool_kp` is fixed by the command line for an episode,
and the haptic handle stiffness is also configured rather than inferred.

At commit time, the recorder generates a scalar `stiffness_0` label from the
slowly filtered force magnitude:

- below `--ac-f-low 2 N`: label `--ac-k-max 16000 N/m`;
- above `--ac-f-high 100 N`: label `--ac-k-min 2000 N/m`;
- between them: linear interpolation.

It then constructs a Pyrite-style virtual target by treating force divided by
that scalar stiffness as a compliance displacement from the demonstrated pose.

This is a useful adaptive-compliance heuristic, but it is not ground-truth human
stiffness estimation. Force alone cannot uniquely identify stiffness: the same
force can arise from a stiff controller with small error or a soft controller
with larger error. True stiffness identification would require controlled
perturbations, measured hand/tool displacement, mechanical deformation, or an
additional human co-contraction/compliance signal.

For training, keep these concepts separate:

- use `wrench_0` as the realistic finite-bandwidth force observation;
- retain `wrench_ground_truth_0` for diagnostics and alternate preprocessing;
- treat `stiffness_0` as a generated policy target, not sensor ground truth;
- use `ts_pose_controller_0` when learning what the simulated impedance
  controller actually received during any anti-windup intervention;
- retain `ts_pose_command_0` when studying what the operator requested.

## 10. Inventory of interventions and hacks

### 10.1 Simulation/controller interventions currently active

| Intervention | Purpose | Main tradeoff |
| --- | --- | --- |
| Remove UR5e; retain floating WSG50 | Eliminate Jacobian, singularity, arm lag, and arm torque artifacts | Does not reproduce real arm reach/inertia |
| Direct Cartesian PD impedance | Smooth, fast pose control with explicit stiffness | Pose error creates force proportional to `tool_kp` |
| Retain gripper mass/inertia | Preserve acceleration and contact dynamics | Still an approximate rigid-body model |
| Body-by-body gravity compensation | Prevent floating gripper from falling without inverse dynamics | Book gravity remains; gripper weight is deliberately hidden |
| Lock both finger sliders closed after every step | Stop contact-driven gripper opening/closing | FlipUp cannot demonstrate grasp aperture |
| Lower floating `tool_kp` from arm's 16000 to 5000, then 4000 | Reduce controller-manufactured contact force | More tracking lag and possible edge loss |
| Automatic near-critical translational/rotational damping | Prevent free rigid-body oscillation | More damping can increase lag |
| Simplified collision geoms, separate visual geoms | Cleaner, less snag-prone contact and stable rendering | Contact shape is an approximation |
| Contact allowlist with visible table/bookend collision | Preserve useful fixture/table contacts | Requires explicit collision maintenance |
| Table/bookend normal anti-windup, default 80 N | Stop stored spring energy through fixed visible surfaces while allowing sliding | Does not currently limit fingertip–book normal force |
| `--tip-softness` | Approximate a compliant fingertip and reduce solver chatter/peaks | More penetration and mushier contact |
| Smooth target-force saturation code (`tool_force_limit`) | Potentially cap Cartesian spring force | Disabled by default; low limits starved the full arm's free motion |
| Target slew limit `--max-speed` | Prevent abrupt pose targets | Global cap can make all movement slow |
| Optional 6-DoF orientation | Let omega wrist command gripper rotation | No wrist torque feedback; rotation is open-loop to the human |

### 10.2 Haptic interventions currently active

| Intervention | Purpose | Main tradeoff |
| --- | --- | --- |
| Exact contact force as default source | Zero free-space phantom force; honest contact direction | Raw solver signal contains high-frequency switching |
| Reject actuator-side estimated force | Avoid 100+ N phantom readings from tracking lag | Requires contact truth in simulation |
| Derive force gain from requested handle stiffness | Decouple simulated `tool_kp` from perceived stiffness | Must still respect device/passivity limits |
| Independent 1 kHz Force Dimension servo | Keep force updates responsive when rendering stalls | Main process and device clocks are asynchronous |
| 2 ms handle-force filter | Reduce very high-frequency handle commands | Adds feedback-loop delay |
| Force-rate slew limit, currently 60 N/s | Remove first-touch thud | Operator receives full force slightly later |
| 10 N handle clamp and simulated-force clip | Protect device/operator from hard jams | Clipping hides force magnitude from touch, though raw data is retained |
| Contact-dependent handle damping | Increase stability without making free space viscous | Damping changes perceived contact dynamics |
| Passivity-margin startup/exit diagnostics | Detect settings likely to buzz or limit-cycle | Conservative approximation, not a proof for every contact |
| Keep modeled sensor out of default haptic loop | Preserve passivity while recording realistic sensor data | Felt force and BC-facing sensed force have different bandwidths |

### 10.3 Sensor/data-collection interventions currently active

| Intervention | Purpose | Main tradeoff |
| --- | --- | --- |
| Two-pole F/T sensor model at every physics tick | Realistic finite bandwidth without losing raw truth | Adds about 10.6 ms low-frequency delay at 30 Hz |
| Store raw and modeled wrench separately at 1000 Hz | Permit offline A/B filtering and force-aware BC | Larger datasets |
| Additional 250 ms causal label filter | Stable adaptive-compliance labels | Too delayed for live control or direct force observation |
| Async RGB at about 30 Hz | Keep camera data without duplicating frames 33× | RGB and numeric streams require timestamps for alignment |
| Low-priority render/plot workers | Prevent the viewer from stalling the force loop | Occasional control catch-up batches remain visible in audit fields |
| Live raw/sensor/handle plots | Distinguish physics chatter, sensor response, and haptic command | Plotting still consumes some CPU |
| Fixed absolute handle home | Keep all randomized robot starts mapped consistently | Requires physically recentering the device before each episode |
| Idle 100 N/m, 2 N-capped recenter pull | Make precise home acquisition practical | Must be disabled before demonstration data begins |
| Home tolerance, speed check, and 250 ms dwell | Prevent starting while the handle is moving | Adds setup time between episodes |
| 100 ms takeover hold and 400 ms force ramp | Avoid a reset/start haptic impulse | Delays full feedback at episode onset |
| Random start prism with 70% center bias | Cover diverse starts while oversampling the common center | Distribution is designed rather than naturally occurring |
| Reject starts with contact >0.5 N or excessive settle error | Prevent unsafe reset impulses and invalid episodes | May bias away from difficult near-contact starts |
| ±20% book mass/size and realistic color randomization | Improve visual/physical robustness | Wider force distribution; nominal mass must match the real task |
| Record wall time, batch size, lateness, and device-servo sequence | Make 1 kHz timing quality auditable | Consumers must actually use these fields when timing matters |

## 11. Interventions tried and rejected or not yet implemented

### Rejected/disabled

- **Actuator-side force estimation:** arm tracking lag appeared as enormous
  free-space force. Exact contact is used instead.
- **Low global controller-force cap on the full arm:** limits at or below about
  90 N prevented the damped arm from reaching the book. The smooth saturation
  path remains in code but defaults off.
- **Large haptic smoothing time constants:** they reduce high-frequency ripple
  but consume passivity margin and can make contact more likely to bounce.
- **Using book mass alone to hit a target force:** changing recent books to 1 kg
  in replay reduced median force by only about 1 N. Mass should match the real
  object, not be used as the main force tuning knob.
- **Lowering friction as the first response:** early high load was predominantly
  normal, not tangential, so friction reduction would risk slipping without
  removing the main force.

### Proposed next steps, not currently implemented

1. **Contact-only approach-speed limit.** Current measured approach speeds were
   58–104 mm/s. A 30–50 mm/s inward limit near the book would reduce true impact
   without slowing upward/tangential motion.
2. **Book-normal anti-windup/force limiter.** Once fingertip–book contact is
   active, cap only normal controller penetration while preserving tangential
   motion. For 18 N at `tool_kp=4000`, the ideal spring-error cap is about
   `18/4000 = 4.5 mm` before dynamic corrections.
3. **Force-dependent inward admittance.** Smoothly reduce inward velocity as
   measured normal force approaches 18–20 N rather than hard-clipping force.
4. **Independent fingertip contact knobs.** Expose time constant, damping ratio,
   and `solimp` width separately. A possible A/B point is 25 ms, ratio 2, width
   6 mm, but it should be validated against real pad deformation.
5. **Try `--tool-kp 3500 --max-speed 0.05`.** This is the simplest available
   command-line experiment for lowering both sustained wedging and one-off
   impact. It may require more operator motion to finish the flip.

## 12. Practical tuning guide

| Symptom/goal | Change first | Do not confuse it with |
| --- | --- | --- |
| Raw simulated force is too high | Lower `--tool-kp`; reduce normal penetration; soften contact if physically justified | `--stiffness`, which mainly changes handle feel |
| First millisecond impact is too high | Lower approach speed; increase physically plausible tip time constant/width | `--force-rate`, which only changes the handle command |
| Force builds 200 ms after touch | Stop continued normal target motion; add book-contact anti-windup | Sensor cutoff, which only changes observation bandwidth |
| Handle feels too weak/strong | Adjust `--stiffness` or explicit `--force-gain` | `tool_kp`, which changes simulation physics |
| Handle buzzes but raw sim force is smooth | Lower handle stiffness, reduce filter delay, inspect passivity margin | Tip softness |
| Raw force chatters but motion is stable | Use finite sensor bandwidth; validate contact geometry and tip compliance | Downsampling the entire dataset |
| BC force input is too noisy | Train from `wrench_0`; keep raw ground truth for audit | `wrench_filtered_0`, which is intentionally much slower |
| Want true human variable stiffness | Add an identification/measurement signal | Current synthetic `stiffness_0` label |
